# Stage G1 plan -- map sites, map format v2, validator, scale-ready LOS and pathfinding

Tag: **design**. Planning document only. Nothing in this document has been implemented or run. Acceptance criteria describe what WILL be checked by `npm run check` and a browser pass at 1366x768.

Roadmap entry: [`docs/roadmap.md`](roadmap.md) section "G1 Map sites and a second map". This plan covers the engine and the format. Map CONTENT (the second map, real callouts, real plant zones) is authored by the owner. No real Valorant map geometry is ever added, traced or approximated.

---

## 1. Goal and non-goals

### Goal

1. **Map format v2.** Maps live as JSON files under `data/maps/<id>.json`, with a `formatVersion`, polygon regions (`site`, `plant-zone`, `spawn`, `callout`), spawn points, walls, and provenance per field and per region.
2. **Loader and validator.** A pure loader/validator in `src/sim/map/load.ts` and a CLI `tools/validate-map.mjs`. Checks: closed simple polygons, integer mm, walls inside bounds, spawns not on walls, plant zones inside their site, unique ids, reachability from every spawn to every site and plant zone.
3. **Drill Hall migrated** to `data/maps/drill-hall.json` with exactly the same walls, site rectangle (now a 4-vertex polygon) and spawn points. Every existing test and characterization fixture stays unchanged.
4. **LOS and collision at real-map scale.** A uniform-grid wall index behind the existing `wallBlocksSegment`, `hasLineOfSight`, `clipSegment` and `wallDepthMmAlongRay`. Results are identical to brute force. A differential test proves it.
5. **Pathfinding.** `findPath(map, from, to): Point[] | null` in `src/sim/map/pathfinding.ts`, integer mm, deterministic tie-breaking. The UI uses it for live right-click moves. The result becomes the waypoints of a normal `move-route` command, so the engine and replays do not change.
6. **Perf budget** for `stepLive` with 5v5 at 50 ms steps, plus a counter-based test that cannot flake and an optional wall-clock bench.
7. **Synthetic fixture map** (`synthetic-grid`, generated by a pure function, unlisted) for perf and differential tests.

### Non-goals

- The second original map and its callouts (owner content). G1 ships the format and tools that it will use.
- Spike plant/defuse (G2). G1 only supplies `plant-zone` regions and `regionsAt`.
- Agent body radius / agent-agent collision. Agents stay points, as today.
- Height layers (roadmap X4).
- Ability-created walls (`vision.wallOrVolume`). The wall index covers static map walls only.
- A map picker UI. It lands when a second listed map exists (open question 5).
- Changing the replay format. Replays keep referring to maps by `mapId`.

## 3. Design

### 3.1 Types (`src/sim/map/types.ts`, new)

`MapDefinition` moves out of `drill-hall.ts` into a types module. `drill-hall.ts` re-exports it so the existing imports in `team.ts` and `DraftPanel.tsx` keep compiling.

```ts
import type { Provenance } from "../../rules/provenance.ts";
import type { Point, Segment, Side } from "../types.ts";

export const MAP_FORMAT_VERSION = 2 as const;

export type MapRegionKind = "site" | "spawn" | "callout" | "plant-zone";

export type MapRegion = {
  id: string;                 // unique across the whole map
  kind: MapRegionKind;
  name: string;               // display name, e.g. "Site A"
  polygon: Point[];           // >= 3 vertices, implicit closing edge, integer mm
  side?: Side;                // required for kind "spawn", forbidden otherwise
  siteId?: string;            // required for kind "plant-zone": id of the parent "site" region
  provenance: Provenance;
};

export type MapFieldProvenance = {
  bounds: Provenance;
  walls: Provenance;
  attackSpawns: Provenance;
  defenseSpawns: Provenance;
};

export type MapDefinition = {
  formatVersion: typeof MAP_FORMAT_VERSION;
  id: string;
  name: string;
  widthMm: number;
  heightMm: number;
  walls: readonly Segment[];
  regions: readonly MapRegion[];
  attackSpawns: readonly Point[];
  defenseSpawns: readonly Point[];
  notes: string;
  provenance: MapFieldProvenance;
};
```

The legacy rect `sites` field is removed in sub-stage G1.6, after `MapView` draws polygons. Until then the loader fills it as the bounding box of each `site` region, so `MapView` keeps working unchanged in G1.1 to G1.5.

`siteId` is an addition to the contract shape in the brief. G1 owns `MapRegion`, the field is optional, and G2 consumes it to name the planted site.

### 3.2 File format (`data/maps/<id>.json`)

The file is compact so that thousands of walls stay readable in diffs. Points are `[x, y]` pairs and walls are `[x1, y1, x2, y2]`. The loader converts them to `Point` / `Segment`.

```json
{
  "formatVersion": 2,
  "id": "drill-hall",
  "name": "Drill Hall",
  "widthMm": 20000,
  "heightMm": 12000,
  "notes": "Original schematic for the milestone 1 drill. Not a Valorant map.",
  "provenance": {
    "bounds":        { "kind": "assumed", "source": "src/sim/map/drill-hall.ts (pre-G1 literal)", "note": "Original schematic; owner to confirm, then retag owner." },
    "walls":         { "kind": "assumed", "source": "...", "note": "..." },
    "attackSpawns":  { "kind": "assumed", "source": "...", "note": "..." },
    "defenseSpawns": { "kind": "assumed", "source": "...", "note": "..." }
  },
  "walls": [[0,0,20000,0],[20000,0,20000,12000],[20000,12000,0,12000],[0,12000,0,0],[8000,0,8000,4800],[8000,7200,8000,12000]],
  "attackSpawns": [[2500,2500],[2500,4500],[2500,6500],[2500,8500],[2500,10500]],
  "defenseSpawns": [[17000,2500],[17000,4500],[17000,6500],[17000,8500],[17000,10500]],
  "regions": [
    { "id": "site-a", "kind": "site", "name": "Site A",
      "polygon": [[15000,3500],[18500,3500],[18500,8500],[15000,8500]],
      "provenance": { "kind": "assumed", "source": "src/sim/map/drill-hall.ts sites[0]", "note": "Rect migrated as polygon." } }
  ]
}
```

(The `"..."` strings are elided in this sketch only. The real file repeats the full source and note.)

**Versioning.**
- Format v1 is the implicit pre-G1 TS literal. No v1 files exist.
- `formatVersion: 2` is the first file format. The loader accepts only `2` and rejects anything else with `unsupported-format-version`.
- Future versions add a pure `migrateMapRaw(raw): unknown` step chain in `load.ts` (v2 -> v3 and so on). A test pins that every file in `data/maps/` is at the current version, so migrations never run silently at runtime.

**Provenance.** Map geometry is not a game number, but the rules still apply. The Drill Hall numbers came from a code literal with no tag, so they migrate as `assumed` with the note "owner to confirm, then retag owner" (open question 1). They are not upgraded on our own. New owner maps use `kind: "owner"`. `verified` and `secondary` are never valid for map geometry, because no real-map source is allowed. The validator rejects them with `provenance-kind-not-allowed`.

### 3.3 Registry (`src/sim/map/registry.ts`, new)

```ts
import drillHallRaw from "../../../data/maps/drill-hall.json";

export type MapEntry = { map: MapDefinition; listed: boolean };
export const MAP_ENTRIES: readonly MapEntry[];   // drill-hall (listed), synthetic-grid (unlisted)
export function getMap(mapId: string): MapDefinition | null;
export function listedMaps(): readonly MapDefinition[];
```

- Each JSON is parsed once at module load with `loadMap(raw)`. Reachability is skipped here (cost). If a shipped file is invalid, module load throws an `Error` that lists the issue codes, so a broken map fails every test immediately.
- `getMap` moves here. `drill-hall.ts` keeps `export { getMap } from "./registry.ts"` so the current imports in `fog.ts`, `run.ts` and `live-round.ts` keep compiling. Those call sites switch to the registry import in G1.1, and the re-export is then dropped.
- `DRILL_HALL` becomes `getMap("drill-hall")!` (exported from `drill-hall.ts`). `DRILL_HALL_DOORWAY` stays a code constant because tests and `default-drill.ts` use it.
- Loaded maps are deep-frozen (`Object.freeze` recursively). The wall index cache then keys on a stable array identity (3.6).
- `tsconfig.json` gains `"resolveJsonModule": true` so the JSON import type-checks. Vite imports JSON natively.

### 3.4 Loader and validator (`src/sim/map/load.ts`, new)

```ts
export type MapIssueCode =
  | "not-an-object" | "unsupported-format-version" | "missing-field" | "bad-type"
  | "non-integer-mm" | "out-of-bounds" | "extent-too-large"
  | "polygon-too-few-vertices" | "polygon-repeated-vertex" | "polygon-explicit-close"
  | "polygon-self-intersects" | "polygon-zero-area"
  | "wall-zero-length" | "wall-out-of-bounds"
  | "spawn-out-of-bounds" | "spawn-on-wall" | "spawn-not-walkable" | "spawn-outside-spawn-region"
  | "duplicate-id" | "spawn-region-needs-side" | "side-not-allowed"
  | "plant-zone-needs-site" | "plant-zone-unknown-site" | "plant-zone-outside-site"
  | "provenance-missing" | "provenance-kind-not-allowed"
  | "site-unreachable" | "plant-zone-unreachable";

export type MapIssue = { code: MapIssueCode; path: string; message: string };   // path like "regions[2].polygon[1]"

export type MapLoadOptions = { reachability?: boolean };   // default false
export type MapLoadResult =
  | { ok: true; map: MapDefinition }
  | { ok: false; issues: MapIssue[] };

export function loadMap(raw: unknown, options?: MapLoadOptions): MapLoadResult;
/** Geometric checks on an already-typed map (used by loadMap and by tests on generated maps). */
export function validateMap(map: MapDefinition, options?: MapLoadOptions): MapIssue[];
```

Checks, all exact integer arithmetic:

| Check | Rule |
| --- | --- |
| integer mm | Every coordinate satisfies `Number.isInteger`. Bounds are `> 0` and `<= MAX_MAP_EXTENT_MM`, so every `orient` product stays an exact double (3.9). |
| closed polygon | `>= 3` vertices. The closing edge is implicit. A last vertex equal to the first is rejected (`polygon-explicit-close`) so that there is one canonical form. No consecutive duplicate vertices. Twice the shoelace area is a non-zero integer. |
| simple polygon | No two non-adjacent edges meet (`segmentsIntersect`). Adjacent edges may only share their common vertex. O(n^2) per polygon is fine for authoring-size polygons. |
| walls inside bounds | Both endpoints lie in `[0, widthMm] x [0, heightMm]`. Zero-length walls are rejected. |
| regions inside bounds | Every vertex is inside the bounds. |
| spawns | Each spawn is inside the bounds and touches no wall (`pointSegmentDistanceSq > 0`). If the map has any `spawn` region for that side, the spawn is `pointInPolygon` of one of them. With `reachability`, the spawn also snaps to a walkable nav cell (`spawn-not-walkable`). |
| unique ids | Region ids are unique across all regions. The map id matches the file name (checked by the tool and the data test). |
| plant zone inside site | `siteId` names a `site` region. Every plant-zone vertex is `pointInPolygon` (closed) of the site, and no plant-zone edge properly crosses a site edge. Vertex containment alone is not enough for concave sites. |
| side rules | `spawn` requires `side`. Other kinds must not have it. |
| provenance | Present on every region and every field. Kind is `owner`, `assumed` or `design` (design is a doc tag, so code kinds `owner`/`assumed` only; see 5). |
| reachability (opt-in) | For every spawn and every `site` / `plant-zone` region, `findPath(map, spawn, probe(region)) !== null`. `probe(region)` is the first walkable nav cell center inside the polygon, in row-major order, which is deterministic. No probe at all means `site-unreachable`. |

Issues are returned in a fixed order: by check, then by path. The tool output and the tests are therefore stable.

### 3.5 Region helpers (`src/sim/map/regions.ts`, new)

```ts
/** Closed test: points on an edge or vertex count as inside. Integer crossing-number with exact orient. */
export function pointInPolygon(point: Point, polygon: readonly Point[]): boolean;
/** Regions containing point, in file order. */
export function regionsAt(map: MapDefinition, point: Point): MapRegion[];
export function regionById(map: MapDefinition, id: string): MapRegion | null;
```

`pointInPolygon` first tests "on edge" (orient == 0 plus `onSegment`). After that, the crossing rule uses the half-open convention on y (`(a.y > p.y) !== (b.y > p.y)`) and compares the sign of an integer `orient`. There is no division, so the result is exact.

### 3.6 Wall index (`src/sim/map/wall-index.ts`, new)

```ts
export type WallIndex = {
  cellMm: number;            // WALL_GRID_CELL_MM
  cols: number; rows: number;
  originX: number; originY: number;   // 0, 0 (walls are validated inside bounds)
  cellStart: Int32Array;     // CSR offsets, length cols*rows+1
  cellWalls: Int32Array;     // wall indices per cell, ascending
  walls: readonly Segment[];
  stamp: Uint32Array;        // per-wall dedupe stamp (scratch)
  query: number;             // current stamp value (scratch)
};

export type WallQueryStats = { queries: number; candidateTests: number };

export function buildWallIndex(walls: readonly Segment[], cellMm?: number): WallIndex;
/** Calls visit(wallIndex) once per candidate wall whose cells the segment touches. */
export function forEachCandidateWall(index: WallIndex, from: Point, to: Point, visit: (i: number) => boolean | void, stats?: WallQueryStats): void;
export function wallIndexFor(walls: readonly Segment[]): WallIndex | null;  // WeakMap cache; null below WALL_INDEX_MIN_WALLS
```

**Cells touched.** A segment "touches" a cell when it meets the cell's closed rectangle. The cell range covering a coordinate `v` is `[ceil(v / s) - 1, floor(v / s)]`, clamped to the grid. A point exactly on a cell boundary therefore belongs to both cells. Walls and queries use the same rasterizer. It walks the columns of the segment's bounding box. For each column, it computes the segment's y-range over that column's closed x-interval with exact integer floor/ceil division of `ay * dx + (x - ax) * dy` by `dx`, and emits the closed row range. Vertical segments (`dx == 0`) emit one column. There is no float DDA, so no cells can be missed through rounding.

**Correctness argument.** This is the claim the differential test checks. If a query segment and a wall share any point `p`, then `p` lies inside the bounds, because walls are validated inside the bounds. It therefore lies in at least one closed cell `C`. Both segments contain `p`, so both touch `C`, and the wall is a candidate. Each existing function is order-independent over the set of walls:
- `wallBlocksSegment` is an "any".
- `clipSegment` keeps `min(t)` (ties are equal values) and sets `bestT = 0` on the collinear case through `Math.min`.
- `wallDepthMmAlongRay` sorts the hit `t`s and uses only the first and last.
So running the unchanged per-wall math on a superset of the intersecting walls gives bit-identical results. Query segments partly outside the bounds are clamped to the grid for cell enumeration only. The math still uses the original endpoints.

**Integration.** The minimal-touch option. The public signatures `wallBlocksSegment(from, to, walls)`, `hasLineOfSight(...)`, `clipSegment(from, to, walls)` and `wallDepthMmAlongRay(from, to, walls)` stay as they are. Each one first calls `wallIndexFor(walls)`:
- If an index exists, the existing per-wall body runs over the candidates only.
- Otherwise (fewer than `WALL_INDEX_MIN_WALLS` walls, such as Drill Hall's 6 or the inline arrays in tests), the brute-force loop runs.
The brute-force bodies stay exported as `wallBlocksSegmentBrute`, `clipSegmentBrute` and `wallDepthMmAlongRayBrute` for the differential test. The per-wall math becomes a shared inner function, so the two paths cannot drift.

`wallIndexFor` caches in a `WeakMap<readonly Segment[], WallIndex>`. Loaded maps are frozen, so `map.walls` identity is stable and the index is built once per map per process. Call sites in `run.ts`, `live-round.ts`, `fog.ts`, the ability resolvers and `previews.ts` do not change.

### 3.7 Pathfinding (`src/sim/map/pathfinding.ts`, new)

```ts
export type NavGrid = {
  cellMm: number;            // NAV_CELL_MM
  cols: number; rows: number;
  walkable: Uint8Array;      // 1 if cell center is >= NAV_CLEARANCE_MM from every wall and inside bounds
  links: Uint8Array;         // 8-bit neighbour mask, bit k = direction k is traversable
};

export function navGridFor(map: MapDefinition): NavGrid;        // WeakMap cache per frozen map
export function findPath(map: MapDefinition, from: Point, to: Point): Point[] | null;
```

- **Grid.** The center of cell `(c, r)` is `(c * cell + floor(cell / 2), r * cell + floor(cell / 2))`, clamped into the bounds, as integer mm. A cell is walkable when `pointSegmentDistanceSq(center, wall) >= NAV_CLEARANCE_MM^2` for every candidate wall. Candidates come from the wall index over the center's clearance box.
- **Links.** Directions are fixed in the order E, SE, S, SW, W, NW, N, NE (bit 0..7). An orthogonal link needs both cells walkable and `clipSegment(centerA, centerB, walls).blocked === false`. A diagonal link also needs both orthogonal neighbours walkable, so paths do not cut corners. Links are computed once per map.
- **Search.** A* over cells with integer costs: orthogonal `NAV_COST_ORTHO` (10), diagonal `NAV_COST_DIAG` (14). The heuristic is octile, `10 * (dmax - dmin) + 14 * dmin`, which is admissible and consistent for these costs. The open set is a binary heap with a total order on the integer triple `(f, h, cellIndex)`, ascending. A node's g is replaced only on a strictly smaller g. Neighbours expand in the fixed direction order. Every key is an integer, so pop order is a pure function of the inputs.
- **Snap.** The start cell is the cell containing `from` if that cell is walkable and `from -> center` is unblocked. Otherwise rings at Chebyshev distance 1..`NAV_SNAP_RADIUS_CELLS` are scanned in row-major order, and the first walkable cell with an unblocked connector is taken. The goal snaps the same way from `to`. If no snap is found, the result is `null`.
- **Fast path.** If `clipSegment(from, to, walls).blocked === false`, return `[to]`. On Drill Hall this keeps every currently unblocked straight move exactly as it is today.
- **Smoothing.** Greedy string pulling over the cell path: from the anchor, advance to the farthest later point `q` with `clipSegment(anchor, q, walls).blocked === false`. This is the same predicate the mover uses, so a returned route never produces `move-blocked` on static walls.
- **Output.** Waypoints exclude `from` and end at `to` when `goalCenter -> to` is unblocked, else at the goal cell center. All values are integer mm. There is no `Math.hypot` and no trig. `null` means unreachable.
- **No per-step cost.** `findPath` never runs inside `stepLive`. It runs on order issue in the UI, or in a `src/tactics` decide function, and its output is a plain `move-route` command.

### 3.8 How routes feed the engine and the UI

- `AgentCommand` `move-route` is unchanged. The UI computes `waypoints = findPath(map, truthPos, dest)` and issues them through the existing `applyCommands` / `issueOrders`. The order log stores the expanded waypoints, so `replayOrderLog` never calls `findPath`. A later change to the pathfinder cannot break old replays.
- **Live right-click (`issueGroupMove`, live branch).** For each agent in the formation, the path runs from the agent's truth position (`liveRef.current.world`, not the interpolated display position, because the sim starts the segment from truth) to its formation destination. With shift (append), the path runs from the last remaining waypoint. If `findPath` returns `null`, the UI falls back to today's straight waypoint and shows "No path; moving straight." in the plan message.
- **Pre-round routes.** Pre-round routes stay straight in G1. `at-waypoint` triggers index `route`, and expanding one click into several points would shift those indices (open question 4).
- **Previews.** `movementPreview` already draws multi-waypoint routes. The live hover preview calls `findPath` for the hover point, throttled to hover-cell changes (`NAV_CELL_MM` grid), so it does not run on every mouse move.

### 3.9 Synthetic fixture (`src/sim/map/synthetic-grid.ts`, new)

export function buildSyntheticGrid(): MapDefinition;   // id "synthetic-grid", pure integer formulas, no RNG

This is a deterministic maze-like layout: a lattice of rooms with doorway gaps, plus short diagonal wall stubs, so that grid cells hold mixed orientations. ## 4. Determinism and fog implications

- **Integer inputs, IEEE-deterministic math.** JS mandates IEEE-754 double semantics for `+ - * /`, so the existing float `t` in `clipSegment` is deterministic across engines. `Math.hypot` and trig are implementation-approximated by the spec. G1 adds no new use of them in the sim: pathfinding costs and heuristics are integers. The existing `distanceMm` (hypot) is unchanged and noted as a risk.
- **Exactness bound.** `MAX_MAP_EXTENT_MM` keeps every `orient` product and every rasterizer numerator below 2^53, so integer predicates are exact.
- **Index equals brute force.** See the argument in 3.6. Characterization fixtures under `tests/fixtures/characterization/` must stay byte-identical. Drill Hall stays below the index threshold, so its code path is literally unchanged.
- **Caches are pure.** `wallIndexFor` and `navGridFor` are pure functions of frozen data. The scratch `stamp`/`query` fields in the index are reset per query and never affect results.
- **Tie-breaking.** A* pops by `(f, h, cellIndex)` and snap scans row-major. `regionsAt` returns file order. Validator issues are sorted.
- **Fog.** Map geometry and regions are public static data. They are not hidden by fog. `findPath` reads only the static map and the issuing side's own positions, so it leaks nothing. A `src/tactics` bot that pathfinds toward a believed enemy position still only sees what O1 beliefs give it. `viewWorld` is unchanged apart from getting faster.
- **Boundary.** `src/sim/map/*` imports only `src/sim/types.ts`, `src/rules/provenance.ts` and `data/maps/*.json`. `src/tactics` may import `findPath`. `src/sim` never imports `src/tactics`.

## 5. Provenance and unknowns

None of these are game numbers. They are engine design choices, and the engine treats agents as points. `NAV_CLEARANCE_MM` is explicitly not a claimed agent body width.

| Value | Tag | Named constant | How to confirm |
| --- | --- | --- | --- |
| Map file format version 2 | design | `MAP_FORMAT_VERSION` in `src/sim/map/types.ts` | n/a |
| Max map extent 1_000_000 mm per axis | design | `MAX_MAP_EXTENT_MM` in `load.ts` | Keeps products < 2^53; raise only with a proof. |
| Wall index cell size 2000 mm | design | `WALL_GRID_CELL_MM` in `wall-index.ts` | Tune with the bench; results are identical for any size. |

#### 6.5 Perf budget (design targets, not measurements)

Load model per 50 ms step at 5v5:
- Auto-engage at most 10 shooters x 5 LOS, spread over a 1000 ms interval, so roughly 3 LOS on average. The worst case is 50 when all shooters align.
- `runDecisions` every 500 ms: 2 x `viewLive` x 25 LOS.
- The UI calls `viewLive` once per animation frame.

| Item | Budget (design) | Constant |
| --- | --- | --- |
| One LOS query, indexed, synthetic-grid | <= 5 microseconds average | `PERF_BUDGET_LOS_US` |
| Candidate walls tested per LOS query | <= 40 average | `PERF_BUDGET_CANDIDATES_PER_LOS` |
| LOS queries per step (worst step, incl. decide) | <= 120 | `PERF_BUDGET_LOS_PER_STEP` |
| `viewLive` (25 LOS + clone) | <= 0.25 ms | `PERF_BUDGET_VIEW_MS` |
| `stepLive` one step, 10 agents, synthetic-grid | <= 1 ms average | `PERF_BUDGET_STEP_MS` |
| `findPath` one call, synthetic-grid, cross-map | <= 20 ms | `PERF_BUDGET_PATH_MS` |
| 5-agent right-click (5 x `findPath`) | <= 60 ms (one frame hitch is acceptable on issue) | `PERF_BUDGET_GROUP_MOVE_MS` |
| Nav grid + wall index build per map (once) | <= 200 ms | `PERF_BUDGET_MAP_BUILD_MS` |
| Pathfinding per step | 0 calls | (asserted) |

Only the counters and the zero-calls rule gate `npm run check`. Wall-clock numbers gate only through the 10x coarse timer, and are otherwise reported by `npm run bench`.

## 10. Risks

1. **Hidden identity cache.** `wallIndexFor` keys on the array identity. A caller that copies `map.walls` (for example with spread) silently drops to brute force: correct, but slow. Mitigation: the perf counter test runs through the real call sites, and maps are frozen so accidental mutation throws.
2. **Rasterizer edge cases.** A missed cell would break identity with brute force. Mitigation: closed-cell ranges, exact integer division, adversarial differential cases on cell lines, and a second cell size in the differential test.
3. **`Math.hypot` in `distanceMm`.** It is outside G1's scope but is the one engine-dependent primitive left in movement timing. G1 adds no new uses. Flag it for a later integer-sqrt change.
4. **Node type stripping for the tool.** `tools/validate-map.mjs` importing a `.ts` file needs a Node version that strips types natively. Mitigation: `tests/data/maps.test.ts` is the gate inside `npm run check`. The tool is a convenience. If Node is too old, the tool prints a clear "needs Node with type stripping" error.
5. **vitest bench availability.** If `vitest bench` behaves differently on the installed vitest major, the bench file is optional and outside `npm run check`. Fall back to a timed script in `tools/`.
6. **Pathed moves change live feel.** Bent routes may surprise players who relied on `move-blocked` to stop at a wall. Mitigation: the fast path keeps unblocked straight moves identical, and there is a fallback message when no path exists.
